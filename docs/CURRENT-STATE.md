# Current State

Last reviewed: 2026-11-06  
Repository image tag: `0.0.107` (from `VERSION`; Azure's active/latest-ready revision must be verified separately.)

Project Pulse App Container is the ASP.NET Core / .NET 10 Azure Container Apps implementation of Project Pulse. This file records repository behavior and the POC observations shared so far; environment-specific configuration and production readiness must be verified separately.

## Implemented in the repository

- The same container image supports the `RTA` polling role and the `SERVICEBUS` retry-processing role, selected with `PROJECT_PULSE_ROLE`. The RTA role continuously polls; this is not an Azure Functions TimerTrigger application.
- `APP_API_MODE` selects RTA or mock source behavior. RTA uses paging; the mock path uses `maxRecords`. Do not assume the mock query parameter is sent to the RTA endpoint.
- The processor reads initial-request input fields from RTA `INITIAL_REQUEST_METADATA` and update input fields from `UPDATE_REQUEST_METADATA`, then processes each RTA record individually. Root-level `REQUEST_TYPE` routes `UPDATE_REQUEST` to the separately configured relative `ApimUpdateAdjudicationPath` using HTTP PUT; other requests use `ApimAdjudicationPath` using HTTP POST. If the update path is empty, it falls back to the general path. APIM requests carry correlation/idempotency information and validate the configured response-token header; `IDEMPOTENCY_KEY` is sent in the `Idempotency-Key` request header.
- For initial-request writeback, downstream API business fields are read from the root response object and translated into RTA `INITIAL_REQUEST_RESPONSE`; RTA's `INITIAL_REQUEST_METADATA` is only the request-side source shape. For update-request writeback, `INITIAL_REQUEST_METADATA` is null and the raw APIM response JSON is stored in `UPDATE_REQUEST_METADATA`; initial-request mapping is unchanged.
- APIM responses are translated into the RTA writeback shape. The original individual RTA item and raw APIM response are retained as JSON strings in `PAYLOAD_REQUEST` and `PAYLOAD_RESPONSE`; the mapped response is included in the appropriate request-type response field. RTA status writeback is configurable.
- Request-history exchange outcomes show stored RTA status PUT attempt metadata when available. If the final batch status confirms a PUT failure but attempt details are missing, the page shows the failure and directs operators to the log stream.
- The Requests page supports optional automatic history cleanup. It is off by default; admins configure a retention age and a separate check interval. The RTA role claims scheduled runs through the shared history table to avoid duplicate cleanup across replicas. Expired request history, poll reconciliation details, and unreferenced payload files are permanently deleted after an enable confirmation.
- Request history groups loaded records by Unique ID into one transaction row. Expanding a transaction shows a visual per-run path through RTA/mock receipt, APIM/backend send and response, Service Bus milestones, and RTA status writeback. The timeline distinguishes a missing stored outcome from success or failure; counts separately show visible transactions, loaded history records, and the total matching history records.
- APIM transport failures and downstream API application errors are classified separately. A downstream API error envelope identified by `errorCode` (such as `ACC-NOTF-001`) is a final application error, even if APIM mirrors its status as HTTP 404 or another non-200. It is written back to RTA and is not sent to Service Bus or the catastrophic notification endpoint. Other actual APIM non-200 responses use the HTTP retry/notification path: statuses in `RetryHttpStatusCodes` are queued to Service Bus, and the failure triggers an RTA `/admin/notifications` POST. A status-like JSON value alone (for example `"status": 404` inside an HTTP 200 response) is not an HTTP status.
- When an APIM response body contains a recognized downstream API error object (for example, `errorCode`, `message`, `errors`, or an embedded error `status`), Project Pulse treats it as a final application error and sends an RTA status update with top-level `STATUS: FAILURE`. For initial requests, both request-type response fields are null; for update requests, the update writeback contract stores the raw APIM response JSON in `UPDATE_REQUEST_METADATA` and leaves `INITIAL_REQUEST_METADATA` null. `API_CALL_HISTORY.RESPONSE_HTTP_STATUS_CODE` records the actual HTTP code; the raw APIM JSON is kept in `RESPONSE_BODY`, error code/message/details go in `ERROR_MESSAGE`, and `ERROR_STACK` is set only when a stack field is supplied. History retains the response body subject to `REQUEST_HISTORY_PAYLOAD_MODE` redaction.
- RTA notifications use `RTANotificationsBaseURL` and `RTANotificationsPath`. They keep `EXTERNAL_CORRELATION_ID` null, include the RTA `REQUEST_ID`/`REQUEST_QUEUE_ID` when available, and carry concise non-payload diagnostics in notification attributes. Failure to enqueue a retry envelope also triggers an RTA notification; if the APIM response was non-200, that notification reports both failures.
- RTA writeback failure logs report the actual number of attempts made, which may be fewer than the configured maximum for non-retryable HTTP responses.
- Configured APIM failure handling can buffer claim retry envelopes in Azure Service Bus. When APIM/backend has already responded but the RTA status PUT fails, Project Pulse stores the exact translated RTA PUT payload in a distinct message. The SERVICEBUS role sends that payload directly to RTA without replaying APIM/backend; scheduled retries stop at `ServiceBusMessageTtlMinutes` (10 minutes by default) and dead-letter if still unsuccessful. Writeback retry messages are gated on RTA health, not APIM health. Service Bus connectivity/certificate configuration is independent of the RTA client certificate trust setup.
- Request history stores transaction metadata in Azure Table Storage and payload bodies in Blob Storage. `REQUEST_HISTORY_PAYLOAD_MODE` supports `FULL`, `PARTIAL`, and `OFF`. `OFF` suppresses payload capture for new history records; it does not remove payloads already stored.
- The admin-only requests page can send a short-lived Service Bus connectivity-test message from the RTA role. The sender logs broker acceptance; the Service Bus worker recognizes and completes the test message without treating it as a claim retry.
- The authenticated request-history UI uses Microsoft Entra sign-in and the `ProjectPulse.Admin` app role, assigned to the `PROJECT_PULSE_ADMINS` group. The UI shows the signed-in user, provides sign-out/navigation, and offers confirmed history cleanup for the last 24 hours, week, 30 days, or all history. Cleanup deletes Table records and removes batch payload blobs only when no remaining history row references them. Cleanup batches Table transactions, scans payload blobs once, and deletes payload files with bounded parallelism; the progress display separates removed history records from deleted payload files.
- `PROJECT_PULSE_ENVIRONMENT` is shown beside the image version and runtime role on the landing, requests, lifecycle ledger, and poll-batch pages. It is read at runtime so a shared image identifies the environment configured on each Container App.
- The admin-only `/ledger.html` lifecycle ledger filters request-history attempts by time range, status, destination, and processor role, and searches across correlation/unique ID, RTA request ID, and batch ID. It shows the exact matching count and paginated records, with a timeline based only on milestones present in stored history. The APIM stage is labeled as an attempt recorded because its timestamp is saved before the network POST; absence of later milestones means the app has no outcome recorded for those stages. The ledger does not expose payload bodies.
- Request details show RTA/mock input, APIM/backend HTTP outcome, and RTA status PUT outcome when recorded. Recent writeback failures include the final attempt's HTTP status or exception category/message; full stack traces remain in the log stream. RTA poll HTTP status is not currently stored per request.
- Timing averages are grouped by record-processing run (one pass on one record), not by poll or unique record; a replay through APIM creates another run. Each card counts only runs with a saved value for that stage. RTA pull duration is associated with each record returned by the poll. The UI also shows **Other processing** (end-to-end minus the measured stages) to expose uninstrumented time. Per-run durations overlap under concurrency and must not be summed as total elapsed time. The Requests page also reports observed RTA throughput: records received divided by wall-clock time from the first receipt to the last completed poll in the selected range. It includes gaps between polls and excludes later Service Bus replays.
- The Requests list can filter to the last 5 minutes, hour, 24 hours, week, or all time. It shows the exact number matching the selected time window and search, plus the number currently loaded; pagination retains the original time cutoff.
- RTA batch processing supports `SEQUENTIAL`, `RTA_ONLY`, `APIM_ONLY`, and `FULL` through `PROCESSING_CONCURRENCY_MODE`, capped by `PROCESSING_MAX_CONCURRENCY` (default 5, bounded by `PROCESSING_MAX_CONCURRENCY_LIMIT`). The cap is per active batch and per replica, and multiple replicas multiply aggregate APIM/backend or RTA load. Polling cycles remain non-overlapping. The Service Bus role also uses the concurrency configuration to process multiple queued messages up to the effective limit.
- Health endpoints, Application Insights logging/telemetry, Docker image build, and GitHub Actions deployment are present.

## POC observations and limits

- A POC transaction has returned a successful APIM/backend payload to Project Pulse. That confirms the APIM response path for that transaction; it does not by itself confirm RTA writeback.
- RTA PUT/writeback must be verified against the target environment. Prior Dev observations included writeback failures because the target endpoint was unavailable or not configured for the attempted request.
- Service Bus errors observed in POC included a TLS certificate-name mismatch. That indicates a Service Bus endpoint/certificate validation problem; it does not prove Project Pulse is presenting the RTA client certificate to Service Bus.
- `/pulse-health` is an application health endpoint, not proof that the application can authenticate to or send to every dependency.
- Timing averages describe the stored sample and selected date range. APIM round-trip time includes the gateway-to-backend path; writeback time can include retries and backoff. Use batch logs to confirm a suspected cause.
- Payload mode changes affect future capture. They do not purge old table or blob records.
- In-memory outage/circuit state resets on process restart. A single replica is the documented POC deployment configuration; safe multi-replica processing has not been established.

## POC deployment configuration

The documented POC target uses one minimum and one maximum replica. Production scale, availability, security, retention, and recovery behavior still require validation.
